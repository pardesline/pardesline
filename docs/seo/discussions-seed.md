# Discussions: categories and starter threads

Enable Discussions (Settings → General → Features → Discussions), keep the default categories **Q&A**, **Ideas**, **Show and tell**, **Announcements**, and post one starter thread in each. `python docs/seo/apply_github.py --discussions` enables the feature; the threads are posted by hand (the GraphQL API needs category ids that only exist after enabling).

## Announcements: pardesline 0.2.0 and what is next

pardesline 0.2.0 is on PyPI: 43 public 3D and medical imaging datasets loadable in one line (Medical Segmentation Decathlon, AMOS, TotalSegmentator, LUNA16, IXI, VerSe, TCIA collections, OpenNeuro, KITTI, Objaverse, Hugging Face repos), one typed object for point clouds, meshes, volumes and label maps over Open3D, PyVista and SimpleITK, 73 algorithms whose defaults are documented and tied to the data, and a local MCP server for AI agents. The documentation is at https://pardesline.github.io/pardesline/.

What is next, in the order we intend to do it: the model registry (one-line access to pretrained models, same pattern as datasets), Gaussian splats as a first-class kind, more datasets, benchmarks regenerated by CI. Each has a tracking issue you can vote on; the README roadmap links them. This thread is for questions about the release.

## Q&A: Which dataset should I start with for organ segmentation on CT?

Starter answer, so the thread shows what a good answer looks like:

For a first model, `msd_task09_spleen` (41 labelled CTs, 1.6 GB, CC-BY-SA 4.0): one organ, one label, portal-venous phase, fast to iterate on. For multi-organ, `amos22` (600 CT and MRI, 15 organs) or `totalsegmentator_ct` (1 228 CTs, 117 structures as one mask role each: `s.liver`, `s.spleen`...). For kidneys with tumours, `hf_kits23` (CC-BY-NC-SA, non-commercial). All three load with `pl.load(name)`; `ds.split(by="id")` gives a patient-level split; `prepare_nnunet_dataset.py` writes the nnU-Net layout. The threshold baseline in `examples/spleen_ct_threshold_segmentation` is the number to beat first.

## Ideas: What should the model manifest contain?

The model registry is the top roadmap item and its manifest schema is the first decision. The draft in `templates/new_model/manifest.json` has: name, task, input (type, modality, spacing, intensity), output (type, labels), source (Hub repo / HTTPS with checksum / torch.hub), runtime (framework, versions, extra packages, GPU, memory), licence (spdx, commercial, requires_agreement, note), provenance (paper, repository, version, trained_on, reported metrics), validated_on, tags. What is missing for your use? Preprocessing that cannot be expressed as spacing + windowing? Multi-input models? Models that need a tokenizer or a prompt (SAM)? Reply with the model you would load first and what the manifest would have to say for it to work.

## Show and tell: What did you build with it?

Post the dataset, the call, the image, and what the defaults did or did not handle on your data. Real industrial and medical cases are the most valuable thing you can contribute: `examples/real_cases/README.md` explains how to make one reproducible, and the "Real case" issue template collects the facts. The maintainers post their own runs here too, starting with the twelve examples in the gallery.
